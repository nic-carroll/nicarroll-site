Security

Security Is Part of How I Build

I am a Chief Information Security Officer who also builds software for schools and universities. The people those tools serve deserve the same care I would expect from any vendor. This page explains how I protect what I build.

The Principles I Build By

Education runs on trust. Families hand schools information about their children, and that information has to be handled accordingly.

Collect Less

The safest data is data a tool never holds. Public demonstrations use made up or publicly reported information, never real student records.

Give Only the Access Needed

People and systems receive the permissions their job requires and nothing more, with roles that separate who can edit from who can publish.

Keep Secrets Out of Code

Deployments authenticate with short lived identity tokens instead of stored passwords or long lived keys wherever the platform allows it.

Fail Safely

When something required for security is missing, a tool should refuse to run rather than quietly run unprotected.

How the Tools Are Protected

Controls match what each tool does. A static website and a multi user platform carry very different risks.

This Website

  • Static pages with no database, accounts, or forms to attack
  • Encrypted connections and a strict browser security policy
  • Automatic deployment with no stored cloud credentials

EduSite School Website Platform

  • Slow, salted password hashing and limits on repeated sign in attempts
  • District, school, and editor roles with separate publishing rights
  • Protection against forged requests and unsafe page content
  • Restricted upload types and a record of administrative actions
  • Automated tests and a beta release before anything reaches production

Georgia School Data

  • Built on publicly released education data
  • Published as static pages with no accounts or visitor data to protect

Milestone Compass Demo

  • Runs entirely in the browser using demonstration data
  • No real sign in, and practice progress stays in the visitor's own browser

How They Are Monitored

Security is not a one time review. Automation handles the constant checks, and a person makes the decisions.

  1. Every Day: Automated ScansEach code repository is scanned for exposed credentials, known vulnerable components, and risky coding patterns. This website is checked for its expected security protections.
  2. Every Week: Dependency UpdatesComponent and build tool updates are proposed automatically so that fixes can be reviewed and applied quickly.
  3. Every Month: AI Assisted Security ReviewAn AI agent reads recent code changes and scan results with a security reviewer's eye and reports what it finds. It only reports, and any change it suggests waits for my review.
  4. Always: Human JudgmentI review the findings, decide what gets fixed and in what order, and approve the changes.

Report a Security Issue

If you believe you have found a vulnerability in anything I build, please email carroll.nic@gmail.com with what you found and how to reproduce it. Please do not post it publicly until it has been addressed, and do not access data that is not yours or disrupt service while testing.

I will read every good faith report and work with you on a fix. No system is perfectly secure, which is why I value hearing from people who find what I missed.
